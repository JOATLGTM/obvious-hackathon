## Problem Statement

Clinical providers recommend supplements in treatment plans, but ordering runs through third-party marketplaces: the provider fronts the money, ships to the patient, and chases an out-of-band reimbursement. Nothing reaches the practice's records, and the margin accrues to the marketplace. This project builds the in-house flow as a working vertical slice: the provider assembles an order in the product, the patient pays directly, and the system computes and persists an auditable split (COGS, provider margin, 75 bps platform fee), plus a provider dashboard for sales and inventory.

## What Makes This Cool

The split receipt: every cent of a paid order accounted for exactly, persisted at the moment of payment, readable like a receipt. The audit surface is the product.

## Premises (PENDING APPROVAL)

1. Fee base: 75 bps of the patient-paid price, computed per line item. The PRD's headline metric (75 bps on GMV) implies the patient-paid base; any base works, undefined does not.
2. Rounding: fee_cents = round_half_up(0.0075 x price_cents) per line; provider margin is the derived plug (margin = price - cogs - fee). The identity cogs + margin + fee = price then holds exactly on every line, so no residual bucket exists. (Refines the review's "platform-takes-residual" suggestion: margin-as-plug is simpler and exactly auditable.)
3. Margin model: the provider sets the patient-facing price; COGS is a stored catalog field. The PRD's "(or margin)" alternative is not built; the seam is documented.
4. Stack: Next.js (App Router) + TypeScript + SQLite + Drizzle + Vitest, delivered as one PR to main.
5. UI is built to the awwwards bar with the split receipt and provider dashboard as hero trust surfaces; if craft and core-flow integrity conflict, integrity wins.

## Cross-Model Perspective

An independent, web-free Sonar cold read of the PRD (verbatim in review artifact art_l2cMYIRP) flagged the same gaps this design resolves: fee basis, rounding, immutable records, idempotent capture, inventory ambiguity, and COGS freezing at order time. ## Approaches Considered

- A) Minimal viable: single-file HTML plus a tiny Node/Express backend and SQLite. Effort: S (human ~1 day / AI ~20 min). Risk: low. Ships fastest, but the data model, the top-graded criterion, reads as an afterthought.
- B) FastAPI backend plus a separate React SPA. Effort: M (human ~2-3 days / AI ~45 min). Risk: medium. Two apps for graders to run, more surface, no benefit at this size.
- C) Next.js full-stack (RECOMMENDED). Effort: M (human ~2 days / AI ~30-40 min). Risk: low. One coherent codebase, TypeScript end to end, a file-based database graders run with one command.
Recommendation: C, because one coherent codebase best demonstrates the graded data-model and seams within the timebox, and AI tooling is strongest there.

## Money Rules (load-bearing)

- All money is integer cents (USD). Floats never touch money.
- cogs and price are frozen at order creation; catalog edits cannot rewrite history.
- Lines carry a quantity; COGS extends per line as unit_cogs x qty.
- At capture, per line: fee = round_half_up(75 bps x extended line total (unit_price x qty)); margin = extended paid - extended cogs - fee. Extended-line rounding is the base-consistent choice: 3 x $10.00 pays 23 cents of fee, not 3 x 8 = 24.
- The split is persisted at capture as immutable split_entries; reads never recompute.
- The payment stub sits behind a one-method interface, is idempotent per order (at most one successful capture; retries and double-submits return the existing split), and models one deterministic failure path: the stub honors a forced-decline flag on the pay endpoint; a declined capture leaves the order unpaid with no split entries and no inventory change, and a retry succeeds.
- Invariant, enforced by tests: for every paid order, sum(cogs + margin + fee) == patient paid, exact.

## Success Criteria (acceptance criteria)

1. Seeded flow works end to end: provider builds an order (select supplements, set prices), patient pays via stub, order shows paid.
2. The paid order's split view shows per-line and total COGS, provider margin, platform fee, and patient paid, in exact cents.
3. Payment is idempotent and failure-safe: double-submitting capture yields exactly one split, and a forced decline leaves the order unpaid with no split and no inventory change, after which a retry succeeds (both tested).
4. Editing catalog price or COGS after payment leaves the recorded split unchanged (test).
5. Table-driven Vitest suite: single item; multi-item; quantity-3 line with extended-line fee rounding (23 cents, not 24); zero-margin (price = cogs + fee); below-COGS price (negative margin, still sums exact); mid-cent fee rounding; sum invariant on every fixture.
6. Dashboard lists sold orders with totals; inventory decrements on paid orders; order submission is blocked when requested quantity exceeds stock on hand; manual inventory adjustments are recorded as inventory_events (delta, reason, timestamp).
7. README documents run instructions and every stub; AI-USAGE.md documents decisions, trade-offs, cuts, what worked, what did not.
8. This design doc is committed at docs/design/supplement-ordering-slice.md.
9. Lint and tests green in CI; browser-verified at 320/768/1280/1920 with screenshots. Under time pressure, the manual-adjust control (criterion 6) and the multi-viewport sweep (criterion 9) drop first; the core flow and split-integrity tests never drop.
